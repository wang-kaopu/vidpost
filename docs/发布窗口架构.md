# 发布窗口架构

## 模块与构建

Electron 主进程、平台实现、服务层和开发脚本统一使用 TypeScript + ESM。`npm run build:electron` 通过 esbuild 生成 `.build/main.js`；sandbox preload 源码为 `preload.ts`，运行产物为 `.build/preload.cjs`。

后端 TypeScript 统一使用仓库根别名 `@/` 引用项目模块，并保留 `.ts` 扩展名；根 `tsconfig.json`、tsx 和 Electron esbuild 构建共享同一映射。ESLint 禁止后端重新引入 `./`、`../` 模块路径。`forge.config.ts` 是唯一例外：Electron Forge 自带的 Jiti 配置加载器不解析 tsconfig paths，因此该文件继续相对引用 `scripts/forge-packaging.ts`。前端 `app` 使用独立 tsconfig 和 Vite 配置，其 `@/` 指向 `app` 根目录，不与后端别名共享解析范围；两侧通过 `@shared/` 访问仓库根 `shared/` 中的跨进程契约。

`shared/electron-api.ts` 是 Electron IPC 的唯一契约来源，集中定义 `ElectronAPI`、`Platform`、发布判别联合、事件 DTO 和 `IPC_CHANNELS`。preload 和正式 renderer 不重复声明接口，也不以 `unknown` 暴露业务参数或返回值。主进程 handler 仍以 `unknown` 接收跨进程数据，只保留普通对象和平台两个通用边界函数，其余必要字段类型检查直接写在对应 handler 中；规范 DTO 通过显式构造剥离额外字段。频道常量在 main 和 preload 之间共享，不建设第二套泛型 invoke/register 框架。

账号探活与账号后台统一使用 `{ accountId, platform }`，后台额外携带 `nickname`；旧 `id`、`account_id` 和 `platformKey` 输入已删除。发布 IPC 只接受 camelCase 的 `coverUrl`、`videoUrl`、`humanTypeId`、`channelId` 和 `videoChannelId`，不兼容 `coverPath`、`videoPath`、`thumbnailPath` 及平台选项 snake_case 别名。抖音必须显式提供 `visibility`，不再默认公开。发布素材引用进入主进程后分成两阶段：HTTP(S) 来源下载到缓存，其他字符串按本地路径使用，物化结果才产生内部 `coverPath` 和 `videoPath`。`videoType` 使用四种后端业务枚举，中文名称仅用于界面展示。

账号基础设施按职责拆分：`account-login-flow.ts` 管理新账号登录状态机，`account-login-window.ts` 只创建登录窗口，`account-backend-flow.ts` 管理已有账号后台的加载、探测和保存状态机，`account-backend-window.ts` 只管理全局唯一后台窗口。`account-browser-window.ts` 统一应用浏览器身份，`src/infra/browser-storage-state.ts` 统一读写和恢复 Cookie 与 Playwright storage-state；登录 Flow 和后台 Flow 各自维护最小 Runtime 接口，不共享运行时抽象。`partition-store.ts` 是账号 partition 映射的唯一实现。四个平台的 `*-account.ts` 只保留各自的 HTTP 探活、登录成功判定和 `Account` 适配类。

视频基础设施以四个 `*-video.ts` 作为稳定门面，`video.ts` 用基础输入接口、平台输入接口和 `Video<TPayload>` 约束调用。Bilibili 与搜狐各拆为 `publish.ts`、`record-status.ts`；百家号额外使用 `media.ts`；抖音使用 `upload.ts`、`electron-runtime.ts`、`record-status.ts`。模块只沿门面到同平台语义模块单向调用，不建立跨平台 HTTP、Cookie、分片工具或目录 barrel。

仓库使用 npm workspace，正式前端位于 `app/App.vue`，`app/src` 保留为后端联调 Demo。

## 当前发布宿主

平台发布按协议能力选择宿主。搜狐、Bilibili 和百家号直接通过 Node.js HTTP 客户端上传并投稿，不创建发布窗口；抖音仍使用 Electron 托管的账号发布窗口。需要页面交互的平台通过 Electron 启动时暴露的本地 CDP 端口接管已有发布窗口。

账号登录仍通过 Electron 窗口完成。登录窗口不向第三方页面注入悬浮关闭按钮，只响应原生标题栏和 `Cmd/Ctrl+W`，不响应 `Esc`。新账号登录窗口和已有账号后台窗口通过共享账号浏览器配置注册导航保护；平台页面经隐藏 iframe 发起的 `bitbrowser:` 外部协议探测会在 `will-frame-navigate` 阶段被静默取消，行为与真实 Chrome 一致，且不影响 HTTP/HTTPS 平台导航。登录窗口保存草稿账号文件后，抖音、Bilibili、百家号和搜狐统一调用 Node.js Axios `ping()` 完成在线校验和昵称读取，不再为登录后的昵称同步创建 Playwright browser/context。四个平台的发布状态查询同样使用 Node.js Axios 直连，不创建 Playwright browser/context。

## 窗口与队列

需要页面交互的发布窗口按全局唯一 `accountId` 复用。每个账号对应一个 Electron persist partition，partition 由 `resolvePartitionForAccount()` 解析。搜狐 HTTP 发布只使用账号 storage-state 文件，不创建或复用发布窗口。

同一个 `accountId` 的发布任务串行执行；不同账号可以并行执行。某个账号的任务失败后，该账号队列暂停，避免后续任务覆盖失败现场。

状态监控不进入发布队列。每个发布任务使用独立的递归 `setTimeout`，因此同账号的多个审核任务可以并发查询；同一任务重复注册会复用已有监控，避免重复轮询。

## 窗口显示规则

发布窗口仅由需要页面交互的平台按需创建。对应发布过程会 `show()` 并 `focus()` 窗口，便于观察自动化执行现场。正常发布成功后会保存 cookie、回到账号 marker 空白页并隐藏。

发布失败、超时或平台返回非成功结果时，窗口保持显示并保留异常发生时的平台页面，方便人工排查。用户关闭已展示窗口时只隐藏窗口，不销毁账号窗口。

账号管理页的“账号后台”独立于自动发布窗口。抖音、Bilibili、百家号和搜狐号分别从平台后台首页进入，并复用账号 ID 对应的 persist partition；登录态失效时由平台自行跳转登录页和跨域同步页。后台 Flow 以首个成功完成的 HTTP(S) 主 frame 作为启动成功标准，`ERR_ABORTED / -3` 只表示当前鉴权导航被替换并继续等待；其他主 frame 错误在启动前直接失败，子 frame 错误不影响启动。首次主页面加载限时 30 秒，成功后取消启动计时且不设置使用超时；后续主 frame 导航失败只记录日志并保留窗口。

账号后台窗口带主窗口父级和 `modal: true`，渲染进程同时显示全屏遮罩；全局只允许一个后台窗口，关闭后真正销毁。窗口只响应原生关闭按钮和 `Cmd/Ctrl+W`，不响应 `Esc`，也不向第三方页面注入关闭按钮。页面请求创建的新窗口全部通过 `shell.openExternal()` 交给系统浏览器。用户在首个主页面成功前关闭窗口时不导出或覆盖账号状态；页面成功后关闭仍等待在途探测并执行最终保存。

发布互斥只由正式前端控制，不在主进程设置发布锁。应用级发布进度中存在 `waiting`、`preparing`、`queued` 或 `publishing` 条目时，点击账号后台提示“发布视频中, 完成后再打开”。投稿 invoke 成功或失败后条目进入终态并解除互斥；后续平台审核状态不参与该判断。后台窗口存在时模态窗口和前端遮罩阻止主界面发起其他操作。

## 账号状态

`accountFile` 仍是优先状态来源。搜狐 HTTP 发布直接读取完整 Playwright storage-state，其中必须包含有效 Cookie、`vuex`、`sp-cm` 和 `dv-id`；缺失字段时要求重新登录，不兼容历史残缺文件，也不回退到浏览器发布。

需要页面交互的平台在发布开始前把账号状态注入 partition，并在成功后回写。搜狐登录必须保存完整 Cookie 与 localStorage，旧的 DOM 填表和点击发布路径已废弃。

四个平台通过 `browser-identity.ts` 读取 `assets/browser-identity/browser-identity.*.json` 中与宿主系统匹配的 Chrome 138 身份。登录窗口统一应用 UA、平台、语言、Client Hints 和宿主时区；账号探活只按各平台 HTTP 协议发送所需字段。日常探活前先检查正式 cookie 文件和已绑定 partition，任一缺失时跳过平台请求并直接同步离线，不为探活自动创建 partition。搜狐还从完整 storage-state 中读取 `accountId`、`sp-cm` 和 `dv-id` 等客户端校验字段。旧 Chrome 148 固定 Windows 富指纹、后台页面 URL、标题和文案探活均已废弃，不提供浏览器兜底。接口判定、异常语义和批处理规则见《账号在线状态检测》。

登录后的最终流程固定为“Electron 登录 → 保存草稿账号文件 → 调用一次 `account.ping(accountFile)` → 创建远程账号”。`online: false` 或 `ping()` 异常都会终止创建。`ping()` 有昵称时直接写入；没有昵称时不判定失败，而是在远程创建返回 ID 后，复用 attributes 更新请求把该 ID 的字符串形式写为昵称。账号创建失败后的回滚范围保持不变。

打开账号后台前，如果正式账号文件结构有效，会先清理账号 partition 中的 Cookie 和 localStorage，再恢复文件中的状态；文件缺失或失效不会阻止打开，平台可以跳转到登录页。后台窗口每 5 秒探测一次尚未恢复的登录态，首次通过 `Account.ping()` 后立即用窗口 Session 替换账号文件并更新远程在线状态和昵称，然后停止周期探测。首个主页面成功后，窗口关闭时无论在线与否都导出最终状态：有效登录更新为在线，主动退出或无效登录更新为离线。重新登录另一个同平台账号允许换绑，但保留系统账号 ID、标签和历史记录。最终导出、探活或远程更新失败时仍关闭窗口，并由账号管理页通知用户重试。

## 定时发布

Bilibili、百家号和抖音使用平台服务端定时能力，不创建本地计时器，也不把任务留在应用内等待。底层定时参数仍按上海时区的 `YYYY-MM-DD HH:mm` 校验，并在平台最小提前量上固定预留 10 分钟上传时间；同账号串行队列中的后续任务不递增计算余量。搜狐仍只允许立即发布。当前渲染器处于发布工作台迁移期，作品页只把作品加入发布页；账号选择由独立抽屉承载，可按平台或标签筛选并为每个作品绑定一个在线账号；发布设置抽屉只根据该账号的平台展示并校验时间控件，但暂不从旧发布计划面板或迁移页提交任务。

Service 层只把空的 `scheduledAt` 规范为 `"0"`，其他非空值原样传给平台。Bilibili 和百家号在各自 `publish.ts` 中转换 Unix 秒，抖音在 `upload.ts` 中转换：Bilibili 定时投稿增加数字 `dtime`，百家号增加十进制字符串 `timer_time`，抖音把数字写入 `item.common.timing`。抖音必须先完成该字段写入和 `JSON.stringify()`，再由 Creator BDMS 对最终 URL、原始 Body 和 UA 生成签名。

发布 Service 在创建远程任务前通过 `normalizePublishText()` 统一清理标题和简介。标题按 Unicode 码点分别限制为百家号 50、Bilibili 80、抖音 30、搜狐 30，简介统一限制为 100；超长内容静默截断，同一结果用于远程任务、平台投稿和审核线索。搜狐不再保留旧的 60 字符上限报错，仅在统一截断后校验平台必需的最小长度。

定时投稿被平台接受后，远程任务仍进入 `reviewing`。`review_state_clues.published_at` 记录提交请求成功的当前时间，不记录计划发布时间。

## 审核状态生命周期

抖音、Bilibili 和百家号投稿成功并写回 `reviewing` 后立即在主进程注册监控，第一次平台查询发生在 30 秒后。立即投稿最多监控到 `published_at + 2 小时`；定时投稿最多监控到 `scheduledAt + 2 小时`。主进程启动后恢复历史任务，退出时停止全部计时器和请求。

平台查询只使用 `review_state_clues.platform_work_id`。平台审核失败更新为 `non_public`，发布过程异常及超时更新为 `failed`。平台 HTTP、网络和响应结构异常只写 `review_state.sync_error`，不改变任务状态。终态写回失败时缓存终态并仅重试后端更新，避免重复请求平台。

主进程为四个平台分别维护 30 秒状态监控，并通过 `publish-task-state-changed` IPC 把终态和同步错误通知给记录页。记录页监听期间合并刷新事件，不建立前端轮询，也不再触发搜狐单次同步。

## 发布进度轻提示

发布任务完成前置校验后，正式前端在窗口顶部居中显示非模态进度浮层。浮层不使用遮罩，不阻断页面操作；点击外部和按下 `Esc` 不会关闭，只能使用右上角关闭按钮。关闭按钮左侧提供独立的折叠按钮；折叠后保持原宽度并只显示标题栏，任务及其后台更新不受影响，标题栏本身不触发折叠。普通状态变化不会自动展开浮层，用户确认新一批发布任务时会恢复展开。关闭仅隐藏浮层，不取消任务，也不停止后台状态更新。应用重启不恢复轻提示，历史结果统一由矩阵发布记录承接。迁移期发布页已接入账号及平台差异化设置，但尚未接入任务提交，因此从作品页“加入发布”或在抽屉保存设置本身都不会创建进度条目。

每个发布任务对应一个条目，按用户确认发布时的计划顺序固定排列，展示平台图标、平台名称、账号、标题、阶段文案和进度条。进度条表达真实执行阶段而非上传字节百分比，因此不展示数字。任务先后经过等待处理、准备素材、等待账号队列和上传发布；立即发布被平台接受后显示“发布完成，审核中”，定时发布被平台接受后显示“预约完成，等待平台发布”。这两个文案只表示投稿请求已成功，不替代后续审核状态监控。

渲染进程通过带 `progressId` 的 `publish` invoke 发起任务。主进程在远程任务创建完成、素材落地完成和实际取得账号队列执行权时，通过 `publish-task-progress` IPC 依次回传 `preparing`、`queued`、`publishing` 阶段；invoke 成功返回代表投稿已被平台接受，异常返回代表发布失败。进度事件发送失败不会中断实际投稿。

浮层打开期间，完成或失败条目保留到用户整体关闭。下一次确认发布会重新打开浮层，仅保留当前应用会话中尚未结束的旧任务并追加新任务，不动态重排。任务失败时条目显示简短原因，并为每个失败任务单独写入一条系统通知；成功任务不重复写入系统通知。
